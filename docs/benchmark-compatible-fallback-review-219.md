# Issue #219：COMPATIBLE 兜底误显示代理延迟

日期：2026-09-19。对应作者[最后一条反馈](https://github.com/Clash-FX/ClashFX/issues/219#issuecomment-5677607356)：应失败的项在另一张图中都出现延迟。

## 修复范围

Mihomo v1.19.24 的 `GroupBase.GetProxies` 在无成员时可能返回内置 `COMPATIBLE`，该节点由 `outbound.NewCompatible()` 创建，使用 Direct 实现。过去 ClashFX 会把它作为普通叶子节点测速，将直连结果映射到外层地区组。

当前修复：

- 识别 `Compatible` 类型和保留名称 `COMPATIBLE`，路径解析返回明确的兜底原因，不生成普通代理测速 target。
- 检查策略组的成员和 `now` 一致性，不允许空组或组外目标被解析成有效代理路径。
- 自动组无实际候选节点时不发起延迟请求；全局和 provider 遍历也排除兼容兜底。
- 缓存读取、菜单实时通知、重新打开菜单和自动组标题都拒绝把 COMPATIBLE 历史显示成地区代理延迟。
- 显示“直连兜底（无代理节点）”或“无可测速代理节点”，不会凭空把直连路径标成代理成功，也不强行改写核心选择。
- 显式配置的 `DIRECT` 仍是合法路径，可以显示它自己的测量结果。

## 修复后的 review

按计划生成 → 自动组复测 → 结果存储/读取 → 菜单刷新复查：

1. 选中的空自动组不能经 deferred retest 绕过兜底过滤。
2. 多层嵌套组和未在 `/proxies` 中列出的 COMPATIBLE 均不产生测量目标。
3. 旧的 532ms COMPATIBLE 缓存和核心 history 不会重新显示；实际节点变成兜底后原有节点延迟也不会留在组行。
4. DIRECT 的合法测速与核心 `now` 的勾选语义保持独立，没有将所有直连统一判为失败。
5. 候选图遍历带 visited 集合，循环或缺失节点不能导致无限遍历。

本次覆盖范围内没有发现剩余阻塞问题。这是针对确定代码路径的修复；尚无作者脱敏配置或现场核心响应，不能据截图断言它是作者环境中唯一的原因。

## 隔离验证

新增两个模型测试和三个真实 AppKit 菜单集成测试：

- 两个地区空组共享兜底时，不生成 COMPATIBLE 测速；同一菜单中的 DIRECT 和真实代理仍产生正确请求。
- 核心缺少 COMPATIBLE 条目、成员为空或 now 指向组外节点时，不产生成功路径。
- 注入旧 532ms 兜底缓存和核心历史后，菜单实时状态与重新打开后的状态都显示兜底说明。
- 在空自动组点击 ReTest，不启动会话、不发出 delay 请求。
- 已显示真实节点延迟的组切换为兜底后，旧值消失，同时真实叶子节点自身的有效值保留。

全套 **139 项测试通过，0 失败**。测试网络由专用 URLProtocol 拦截，不连接用户核心。测试前后 ClashFX PID 为 35483、Mihomo 核心 PID 为 94503，系统代理配置的 SHA-256 摘要一致。完整 App 编译在临时副本中执行并通过，不安装、不启动该构建。
